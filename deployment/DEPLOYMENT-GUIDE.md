# Deployment guide — Jamia-tur-Raza Ghousia Mehria

This project supports a **single-service production deployment**: Vite builds the React website and Express serves the built pages and `/api` from the same public origin. That removes the need to configure a separate production frontend API URL for the recommended deployment.

## Option A — Easiest production route: Render + MongoDB Atlas

1. Put the complete project folder in a private or public GitHub repository. Do **not** upload `.env` or any real secrets.
2. Create a MongoDB Atlas database and database user. In Atlas Network Access, allow the deployment platform to connect. Prefer the narrowest practical access rules; only use a broad temporary rule if you understand the exposure and replace it afterward.
3. In Render, choose **New → Blueprint** and connect the repository containing `render.yaml` and `Dockerfile`.
4. Render will request values for `MONGO_URI`, `ADMIN_NAME`, `ADMIN_EMAIL`, and `ADMIN_PASSWORD`. Enter them in Render's environment form. Use a strong unique admin password. `JWT_SECRET` is generated by the Blueprint; do not replace it with a weak value.
5. If Render assigns a different URL than `https://jamia-tur-raza-ghousia-mehria.onrender.com`, open the service's Environment settings and change `CLIENT_URL` to the exact deployed website origin (scheme + domain, no trailing slash), then redeploy.
6. Once the deployment is live, open the service Shell if your plan provides it, set the working directory to `/app/backend` if needed, and run:

   ```sh
   npm run seed
   npm run create-admin
   ```

   If shell access isn't available on your plan, initialize content/admin locally using the same production database only after confirming the target database, or use a plan that supports a one-off/shell command. Never point seed at a database with important content until you have reviewed the seed script and made a backup.

7. Open `https://YOUR-RENDER-DOMAIN/api/health`. Expected response should include `"ok":true`, `"api":"running"`, and `"database":"connected"`.
8. Open `/admin/login` and sign in with the admin email/password configured in Render. After the first login, test the public contact form, the admin enquiries list, program/notice creation and deletion, English/Urdu switching, and mobile pages.

Render's free plans and runtime behaviour may change. Check current provider limits before launch; a free instance may sleep or have resource limits. For a real client launch, consider reliable hosting and database backups.

## Option B — Run everything locally with Docker

Requirements: Docker Desktop (including Docker Compose) and an internet connection for first-time image/package downloads.

1. Copy `.env.example` to `.env` in the project root.
2. Edit `.env` and set at least:
   - `MONGO_URI` to your MongoDB Atlas or other reachable MongoDB URI
   - `JWT_SECRET` to a long unique random secret of 32+ characters
   - `ADMIN_NAME`, `ADMIN_EMAIL`, and `ADMIN_PASSWORD` to the intended administrator's details
   - `CLIENT_URL=http://localhost:5000`
3. Build the single application image:

   ```sh
   docker compose build
   ```

4. Seed the seven confirmed programmes and year-round admissions notice:

   ```sh
   docker compose run --rm jamia-website npm run seed
   ```

5. Create/update the admin account:

   ```sh
   docker compose run --rm jamia-website npm run create-admin
   ```

6. Start the website and API:

   ```sh
   docker compose up -d
   ```

7. Visit `http://localhost:5000`; health check: `http://localhost:5000/api/health`.

To stop it: `docker compose down`. To view logs: `docker compose logs -f jamia-website`.

## Option C — Local development without Docker

Terminal 1 (backend):

```powershell
cd backend
Copy-Item .env.example .env
# Edit backend/.env with MONGO_URI, JWT_SECRET, ADMIN_NAME, ADMIN_EMAIL, ADMIN_PASSWORD.
npm install
npm run seed
npm run create-admin
npm run dev
```

Terminal 2 (frontend):

```powershell
cd frontend
Copy-Item .env.example .env
npm install
npm run dev
```

Open `http://localhost:5173`. The local Vite app calls `http://localhost:5000/api` by default. Keep the backend and frontend terminals running while developing.

## Important environment settings

- `MONGO_URI`: private database URL; never include it in frontend environment variables.
- `JWT_SECRET`: a unique random secret of at least 32 characters. Treat it like a password.
- `ADMIN_PASSWORD`: at least 12 characters, unique, and never reuse a personal password.
- `CLIENT_URL`: exact frontend origin allowed by the backend CORS policy. It must match the deployed site domain exactly.
- `TRUST_PROXY=1`: use when hosting behind a trusted reverse proxy such as Render; keep `0` for ordinary local use.
- `SERVE_FRONTEND=true`: allows Express to serve `frontend/dist` in the recommended single-service production deployment.
- `VITE_API_URL`: only needed for a separate frontend/backend hosting setup. For a same-origin production build the frontend defaults to `/api`.
- `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`: optional server-only settings. Set all three in the hosting dashboard to send new media uploads to Cloudinary and enable automatic image format/quality delivery. Never expose these values to the frontend. Existing local media continues to work; new replacements are stored in Cloudinary.

## Production launch checklist

- [ ] Confirm Urdu spelling, programs, owner's public contact details, and address with the institution.
- [ ] Confirm permission for all published event images, especially recognizable children.
- [ ] Verify the exact Google Maps pin and address.
- [ ] Set a strong admin password and rotate any credentials shared during development.
- [ ] Confirm MongoDB Network Access, database user permissions, backups, and restore process.
- [ ] Confirm public forms submit and create private enquiry records.
- [ ] Confirm admin role checks and test that logged-out visitors cannot access admin endpoints.
- [ ] Test at 320, 360, 375, 390, 412, 768, 1024, and 1440 CSS-pixel widths, including Urdu RTL.
- [ ] Check all pages, links, keyboard focus, form states, broken images, and browser console errors.
- [ ] Check performance on an actual Android phone and a slower connection.
- [ ] Have the institution approve the included `/privacy` draft; define who can read enquiries and how long records are retained.
- [ ] Add a final production domain, HTTPS, backup plan, and monitoring contact.

This bundle includes deployment configuration, but deployment isn't complete until the owner configures hosting/database credentials and runs the checks above.


### Uploaded media persistence and Cloudinary

Without Cloudinary credentials, the media library uses local disk storage. By default files are stored in `backend/uploads/media`. On a host with a persistent mounted disk, set `MEDIA_UPLOAD_DIR` to the mount path (an absolute path) in the server environment. Docker Compose defines a named `jamia-media` volume. To use Cloudinary, configure all three `CLOUDINARY_*` variables in the server environment; partial configuration prevents startup. Existing local uploads are not migrated automatically and should be backed up separately.
